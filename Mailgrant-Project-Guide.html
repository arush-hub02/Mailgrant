04 / PRIVACY BY DESIGN

Trust deserves
more than a promise.

Here is what protects the data—and where the limits are.

A

Only approved mail is shared.

Direct Gmail mode fetches approved senders but receives broader mailbox read permission. Forwarding can keep unrelated mail out entirely. Both paths recheck senders, subjects, authentication, and recipients.

B

Permissions live on the server.

Membership, company permission, access windows, and message expiry are checked before content is returned. Hiding a button is never the security boundary.

C

Less data to expose.

Codes-only rules store the extracted value instead of the full body. Sensitive retained content is encrypted with AES-GCM before database storage.

D

Expiring by default.

Rules default to 15-minute retention. Expired content is inaccessible immediately; a scheduled job removes it from active storage.

The limits matter, too.

Direct Gmail grants the app mailbox-wide read permission; sender limits are enforced by our code. The backend processes emails; this is not end-to-end encryption. An approved recipient can copy what they see. Revoking access stops future reads here, but cannot recall a copied code or end an existing session in Claude or another service. Deleted data may remain in infrastructure backups until those backups expire.

What is implemented in this project?+

Google OAuth with PKCE and nonce checks; multiple Gmail accounts under one dashboard, pinned mailbox identities, encrypted refresh tokens, fixed-window paginated syncing and disconnect; secure, hashed sessions; multi-workspace membership; private invitations bound to a Google account; scoped access keys, multiple saved keys and a combined recipient inbox, no-expiry options, atomic message-open limits, individual removal and revocation; exact-sender and subject rules; code/link extraction; plain-text reading; expiring grants; member removal; rule pause/delete; owner-only Gmail confirmation handling; address rotation; message deletion; configuration export; activity history; scheduled cleanup; and an isolated sample-data demo.

What must be configured before real mail works?+

A Cloudflare account, D1 database and migrations, Google OAuth web client with Gmail API enabled, application origin, and 32-byte encryption key. A free workers.dev address works without a custom domain. Each linked Gmail separately consents to read access and can differ from the dashboard login. Add every authorizing Google account as a test user while the OAuth project is in Testing. Optional forwarding requires an inbound domain and Gmail filters. Public Gmail integration can require Google verification and a security assessment.

What is intentionally outside this first release?+

Sending or deleting originals in Gmail, automatic email delivery of invitations, background Gmail polling while everyone is away, attachments, HTML email execution, guaranteed support for every service’s code format, and termination of third-party account sessions. BCC-only messages and failed sender authentication are rejected. Use native team seats in third-party services when you need restricted access within those services.

Can this remain free?+

Cloudflare Workers, D1, and inbound Email Routing have free allowances. This is a reasonable starting point for small usage, not unlimited free hosting. Direct Gmail mode requires no purchased domain. Optional forwarding requires a domain. Growing traffic or storage can require a paid plan, and a public Gmail integration can have verification/assessment costs. The live multiuser app is deployed to your own Cloudflare account; this hosted showcase contains sample data only.
